# Where the customisations live

Everything in this repository is regenerated by `speakeasy run`. This is the map of
what survives that, and how. Read it before changing anything, because the wrong
layer either gets overwritten or fights the generator on every run.

There are **four** places customisation lives, in increasing order of fragility.

---

## 1. The overlay — `.speakeasy/terraform_overlay.yaml`

Changes to the API description itself, applied to the spec pulled from the Speakeasy
registry before generation. The source spec is not in this repository and cannot be
edited here, which is why this file exists.

Wired in through `.speakeasy/workflow.yaml`:

```yaml
sources:
  Authlete-OAS:
    inputs:
      - location: registry.speakeasyapi.dev/authlete/sdk-workspace/authlete-oas:main
    overlays:
      - location: .speakeasy/terraform_overlay.yaml
```

Currently carries:

| What | Why |
|---|---|
| `x-speakeasy-entity` / `-operation` on service and client | Without these no Terraform resources are produced at all |
| `Service#create` / `#delete` pointed at the IdP endpoints | The cluster's `/api/service/create` produces org-orphaned services |
| `clientId` and `serviceId` path params retyped to int64 | Type mismatch against the schema field blocks generation |
| `x-speakeasy-match: apiKey` | Tells read, update and delete where the identifier comes from |
| `additionalProperties: false` on client | An open object cannot be given a stable generated type |
| `x-speakeasy-param-sensitive` on secrets | Conceals them from console output |
| `x-speakeasy-terraform-custom-type` on the JWK Set fields | Stops a phantom diff — see section 2 |

**Safest layer. Prefer it.** It is declarative, reviewable, and cannot conflict.

---

## 2. Hand-written files the generator does not know about

Ordinary Go in packages Speakeasy never writes. Verified to survive regeneration
untouched — they are not tracked in `.speakeasy/gen.lock`.

| File | Purpose |
|---|---|
| `internal/provider/idp_routing.go` | Reroutes IdP traffic to a customer's own host; injects `apiServerId` |
| `internal/provider/customtypes/jwks.go` | Compares JWK Sets by JSON meaning rather than bytes |
| `internal/provider/functions/jwk_from_pem.go` | The `jwk_from_pem` provider function |

Plus a `_test.go` beside each.

Two of these are reachable only because `gen.yaml` names them:

```yaml
terraform:
  additionalFunctions:
    - importAlias: authletefunctions
      importLocation: github.com/speakeasy/terraform-provider-authlete/internal/provider/functions
      function: authletefunctions.NewJWKFromPEMFunction
```

and because the overlay points `x-speakeasy-terraform-custom-type` at the customtypes
package. `additionalResources`, `additionalDataSources` and
`additionalEphemeralResources` work the same way if more is ever needed.

**Second safest. Put logic here and keep section 4 thin.**

---

## 3. Generator configuration — `.speakeasy/gen.yaml`

Switches that change what gets generated:

| Setting | Effect |
|---|---|
| `environmentVariables` | `AUTHLETE_TOKEN` → `bearer`, `AUTHLETE_SERVER_URL` → `server_url` |
| `additionalProviderAttributes` | Adds `http_headers` and `tls_skip_verify` |
| `additionalFunctions` | Registers `jwk_from_pem` |
| `enableOperationServers: true` | Required for the IdP operations' separate host |
| `persistentEdits.enabled` | Turns on the three-way merge in section 4 |

Speakeasy rewrites parts of this file, so expect cosmetic churn — it normalised
`enabled: true` to `enabled: "true"` on first run.

---

## 4. Persistent edits to generated files

Direct edits to files carrying `DO NOT EDIT`, preserved by a three-way merge against
the last pristine generation. **Requires this directory to be its own Git repository**,
which is what the merge uses for its baseline.

Only one file is edited this way:

**`internal/provider/provider.go`** — three hunks, each marked
`// idp_host: hand-added, see idp_routing.go`:

1. `IdpHost` on the provider model struct
2. the `idp_host` schema attribute
3. wrapping the HTTP transport in `NewIdpRoutingTransport`

**Most fragile layer.** A conflict here shows up as Git-style markers in generated Go,
and the build breaks. Keep the hunks small and the logic in section 2, so a conflict is
a three-line fix rather than a re-implementation.

### The example is not in this category

`examples/provider/provider.tf` is hand-written but behaves gently: `tfplugindocs`
embeds it verbatim into `docs/index.md`, which is the page the Terraform Registry
serves. So **edit the example, never `docs/index.md`** — the docs follow automatically.
The same applies to every `examples/resources/*/resource.tf` and `import.sh`.

---

## Outside all of this

`testing/` is a hand-written harness with no relationship to the generator. Verified to
survive the "Cleanup Orphaned Files" step.

---

## After changing anything

```bash
speakeasy run --skip-versioning
grep -rn '^<<<<<<<' --include='*.go' .   # must be silent
go build ./... && go test ./internal/provider/...
cd testing && ./run.sh plan
```

And against a live organisation, because the spec and the server do not always agree —
that is how the orphaning create endpoint was found:

```bash
cd testing && ASSUME_YES=1 ./run.sh apply && ./run.sh plan && ASSUME_YES=1 ./run.sh destroy
```

The second `plan` must report **No changes**. A diff there means something stopped
round-tripping, which is the failure mode that reaches customers as permanent plan noise.

## 5. The README

`README.md` is generated in sections, each wrapped in a `<!-- Start X [id] -->`
and `<!-- End X [id] -->` pair. Everything between a pair is rewritten on every
run, silently: the README is spliced rather than three-way merged, so an edit
inside a pair disappears without a conflict and without a line in the run
output. It can never be protected by persistent edits either — the generator
hard-codes `^README\.md` as untrackable.

Three things work:

- **Write above the first marker or below the last one.** Both positions are
  left alone. The generated table of contents indexes hand-written sections and
  re-indexes them if they move.
- **Freeze one section** with a `<!-- No X [id] -->` line immediately above its
  `Start` marker. The `[id]` must match; the title text is free-form. The
  Installation block is frozen this way, which is why its version pin has to be
  updated by hand at release time.
- **`.genignore` the whole file**, if we ever want to own it outright. Not used
  today, since the generated sections are worth keeping current.

Feeding the Installation block from `examples/provider/provider.tf` looks like
it should work — that section renders the file's contents — but it is not
deterministic. Four identical runs produced the annotated block twice and the
generic snippet twice. Hence the freeze.

`docs/` is a different case again: it is rebuilt wholesale by `tfplugindocs`,
hand-written files there are deleted, and `.genignore` does not save them.
Guides belong in `templates/guides/*.md.tmpl`, which renders into `docs/guides/`
and survives.

## 6. A guard Terraform provides that the generated code switches off

Terraform checks, after every apply, that the provider returned what it planned.
When they differ it stops with "Provider produced inconsistent result after
apply", naming the attribute and both values. That is how the ecosystem surfaces
a server quietly ignoring or rewriting input.

The generated create and update end with:

```go
data.RefreshFromSharedService(ctx, res.Service)   // fill from the API response
refreshPlan(ctx, plan, &data)                     // then overwrite with the plan
resp.State.Set(ctx, &data)
```

The second line means the response and the plan can never disagree, so the guard
never fires. It is emitted unconditionally for every create and update — there is
no gen.yaml key, no extension, and no `x-speakeasy-*` annotation that disables
it.

It is not careless. A generator serving hundreds of APIs cannot know which fields
a server legitimately normalises — reordering a list, trimming whitespace,
filling a default — and each of those would raise the error during a healthy
apply. "Never error" is the defensible default when the server is unknown.

The cost for us is that a field the server silently ignores produces no signal at
all. `hsks`, `metadata` and `sns_credentials` were each found by someone noticing
a plan that never settled, not by the provider saying anything. The next one will
be found the same way.

Removing the line is possible — both resource files are tracked for persistent
edits — but it would be two hand edits in generated files, to re-enable an alarm
whose false-positive rate against Authlete is unmeasured. The experiment is
cheap: delete the line locally, run `testing/run.sh` through create, update and
re-plan, and count the errors. If two or three fields normalise, mark them and
keep the guard. If forty do, put it back. Not yet done.
